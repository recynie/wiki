# Site Reliability Engineering

## 概述

SRE（Site Reliability Engineering，网站可靠性工程）是将软件工程方法应用于运维的学科，通过自动化、可度量的方式提升系统可靠性。Google 于 2003 年率先提出并实践 SRE 理念。

## 核心原则

### DevOps 与 SRE 的关系

- **DevOps**：强调开发与运维协作，打破壁垒
- **SRE**：将运维视为软件问题，用工程化手段解决

两者目标一致（快速交付 + 稳定可靠），但 SRE 更强调 Toil（重复性人工工作）的自动化。

### SRE 团队职责

1. **可用性**：「九个九」目标（99.9999999%）
2. **延迟**：P50/P95/P99 延迟指标
3. **容量**：资源利用率优化
4. **故障处理**：快速响应与恢复
5. **变更管理**：安全发布、渐进式部署

## 服务水平指标（SLO/SLI/SLA）

### SLI（Service Level Indicator）

服务水平的具体量化指标：

```
常见 SLI 指标：
- 可用性：成功请求 / 总请求
- 延迟：请求响应时间
- 吞吐量：QPS/TPS
- 错误率：5xx 错误占比
```

### SLO（Service Level Objective）

目标服务水平，由 SLI 定义：

```
SLO 示例：
- 99.9% 可用性（每月宕机 < 8.7 小时）
- P99 延迟 < 500ms
- 每日成功处理 100 万订单
```

### SLA（Service Level Agreement）

对用户的承诺，违反时需赔偿：

| 等级 | 每月 downtime | 可用性 |
|------|---------------|--------|
| 99% | 7.3 小时 | 两个九 |
| 99.9% | 43.8 分钟 | 三个九 |
| 99.99% | 4.38 分钟 | 四个九 |
| 99.999% | 26 秒 | 五个九 |

## 错误预算（Error Budget）

错误预算是 SLO 与 100% 之间的差距：

```
错误预算 = 100% - SLO

示例：
- SLO 99.9% → 每月允许 0.1% 错误
- 假设每月 100 万请求 → 允许 1000 个失败请求
```

**错误预算策略**：

- 预算充足：可加快发布节奏
- 预算耗尽：暂停新功能发布，专注可靠性修复
- 监控错误预算消耗速率

## Toil（辛劳）管理

Toil 是指重复性、可自动化的人工运维工作。

### Toil 特征

- 手动作业
- 重复性工作
- 被动响应（非主动发现）
- 无持久价值

### 目标

SRE 团队应将 Toil 控制在 **50% 以下**：

```
┌────────────────────────────────────────┐
│           SRE 工程师时间分配            │
├─────────────────┬──────────────────────┤
│   50%+  Engineering Work  │   50%  Toil │
│  (自动化、系统优化、新功能)  │   (手工运维)  │
└─────────────────┴──────────────────────┘
```

## 监控与告警

### 监控体系

```bash
# 黄金信号（Golden Signals）
- Latency    # 延迟
- Traffic    # 流量
- Errors     # 错误
- Saturation # 饱和度（CPU、内存、磁盘）
```

### 告警设计原则

- **P95/P99 告警**：而非平均值
- **单一信号**：每个告警对应单一根本原因
- **消除噪音**：Alert fatigue 会导致忽视

### 监控工具

| 工具 | 用途 |
|------|------|
| Prometheus | 指标收集与查询 |
| Grafana | 可视化仪表盘 |
| ELK Stack | 日志收集分析 |
| Jaeger | 分布式追踪 |

## 事件管理

### 事件分级

| 等级 | 定义 | 响应时间 | 示例 |
|------|------|----------|------|
| SEV-1 | 核心服务不可用 | 立即 | 网站完全宕机 |
| SEV-2 | 部分功能受损 | 15 分钟 | 支付失败 |
| SEV-3 | 非核心问题 | 1 小时 | 报表延迟 |
| SEV-4 | 轻微问题 | 24 小时 | UI 显示异常 |

### 事后分析（Postmortem）

**非惩罚性文化**：重点是学习和改进，而非追责。

```markdown
# Postmortem 模板

## 事件概述
- 时间、影响范围、持续时间

## 时间线
- 按时间顺序记录关键事件

## 根本原因分析
- 5 Whys 分析法

## 改进措施
- 立即修复
- 长期改进
- 预防措施

## 行动项追踪
- 具体负责人和完成时间
```

## 变更管理

### 变更风险来源

- 新代码部署
- 配置变更
- 基础设施变更

### 安全发布实践

- **灰度发布**：逐步扩大新版本覆盖范围
- **金丝雀发布**：先切换小比例流量
- **回滚机制**：快速恢复到上一稳定版本
- **特性开关（Feature Flag）**：在线切换功能开关

```
发布节奏：
┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
│ 1%   │──▶│ 10%  │──▶│ 50%  │──▶│ 100% │
│ 灰度  │   │ 验证  │   │ 扩量  │   │ 完成  │
└──────┘   └──────┘   └──────┘   └──────┘
```

## 容量规划

### 水平扩展 vs 垂直扩展

- **水平扩展**：增加更多机器实例
- **垂直扩展**：升级单机硬件配置

### 容量规划流程

1. **需求预测**：基于业务增长率
2. **压力测试**：确定系统瓶颈
3. **预留容量**：应对突发流量
4. **成本优化**：合理配置资源

## 混沌工程

通过主动注入故障来验证系统韧性。

### 原则（Chaos Engineering Principles）

1. 定义「稳态」行为
2. 假设对照组与实验组表现一致
3. 注入真实世界故障
4. 持续运行实验

### 工具

- **Chaos Monkey**：随机终止 EC2 实例
- **LitmusChaos**：Kubernetes 混沌工程
- **Gremlin**：多维度故障注入
